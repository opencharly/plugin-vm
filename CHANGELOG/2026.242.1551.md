# 2026.242.1551 — feat(vm): screenshot, sendkey, type and seed — the verbs for a guest you cannot ssh into

## Summary

An ISO-installed guest that will not accept SSH cannot be diagnosed with charly at all.
Over several days of investigating exactly that, every question about the guest was answered
by **leaving charly**:

| The question | What was actually run |
|---|---|
| what is on the guest's screen? | `virsh screenshot` → `convert x.ppm x.png` (ImageMagick) |
| what is on the screen of a **qemu**-backend guest? | `socat - UNIX:monitor.sock` + `screendump` |
| the installer is at a prompt — can I answer it? | `socat` + `sendkey`, one keystroke per connection |
| what did charly actually put on the answers volume? | `isoinfo -i seed.iso -R -x /authorized_keys` |

That is a product defect in its own right. The moment charly cannot answer a question about
its own VM, the operator leaves charly and the answer stops being **reproducible** — nobody
can re-run it, no bed can assert it, and the next person starts from zero. **R4a — the
missing capability is the bug**, and documenting the `virsh` incantation instead would have
made it permanent.

Four verbs, none of which need the guest to be reachable:

```
charly vm screenshot <vm> [-o out.png]                    # what is on the screen RIGHT NOW
charly vm sendkey    <vm> alt-f2 ret                      # drive it when SSH is what is broken
charly vm type       <vm> "systemctl status sshd"
charly vm seed ls    <vm> [--domain <deploy>]             # what is ON the answers volume
charly vm seed cat   <vm> user_credentials.json [--domain <deploy>]
```

All four work on **both** backends — `virsh` for libvirt, a minimal QMP client for qemu —
the same split `vm console` already makes. A verb that silently works on one backend only is
a half-cutover, not a capability (R2).

## Three defects found by RUNNING these, not by reading

**1. `virsh screenshot` returns PNG; qemu's `screendump` returns PPM.** Measured on the same
host, minutes apart:

```
virsh screenshot  →  "\x89PNG\r\n\x1a\n…"                 (libvirt, virtio-vga head)
qemu screendump   →  "P6\n720 400\n255\n\x00…" (864015 bytes)
```

The first live invocation failed loudly, which is the design working:

```
charly: error: command "vm": captured screen is "\x89PNG", not a binary PPM (P6)
```

So the format is now **sniffed** (`capturedScreenToPNG`), never assumed. Assuming either one
breaks half the guests; trusting the file extension writes a file no viewer can open. The
two evidence lines above are asserted by a test, not just quoted here.

**2. The PPM reader was off by one byte.** `ppmToken` consumes the whitespace that terminates
each header token — including the one before the pixel data — so the extra `ReadByte()` was
eating the first pixel, shifting every subsequent one and dropping the last row. Caught by
the round-trip test, which asserts a specific pixel's *colour* rather than "a PNG appeared":

```
--- FAIL: TestPpmFileToPNG_RoundTrip
    ppmFileToPNG: captured screen is truncated at row 4 of 5: EOF
```

**3. qemu reports a refused key in the reply TEXT with a ZERO QMP status.**

```
sendkey nosuchkey  →  return: "invalid parameter: nosuchkey"   (QMP status: success)
```

A client that reads only the status reports success for keys the guest never received — and
the operator then concludes the **guest** is unresponsive. `sendKeysOverQMP` checks the text;
NC4 below is the control.

### The QMP client is driven against a REAL qemu, not a mock

A hand-written protocol client is exactly the kind of code that passes against a mock written
from the same misreading that produced the client. The two things most likely to be wrong —
the greeting/capabilities handshake, and async `event` frames arriving between a command and
its reply — are properties of qemu's actual behaviour, so qemu is what answers:

```
$ go test -count=1 -v -run TestQMP_ ./

--- PASS: TestQMP_SendkeyReportsAnUnknownKey (0.06s)
ok  	github.com/opencharly/plugin-vm/candy/plugin-vm	0.182s
```

These drive `screendumpOverQMP` / `sendKeysOverQMP` — the **production** helpers, split out
of socket discovery for exactly this reason — not a re-implementation of them in the test.
The test skips cleanly where `qemu-system-x86_64` is absent.


`r10c.png` reads `Arch Linux 7.1.11-arch1-1 (tty1)` / `archlinux login:`. Then, with **no
SSH, no network and no guest agent**:

```
$ charly -C charly vm type check-arch-vm "root" --no-enter    # exit 0
$ charly -C charly vm sendkey check-arch-vm ret               # exit 0
$ charly -C charly vm screenshot check-arch-vm -o r10e.png
```

`r10e.png` reads:

```
archlinux login: root
Password: _
```

The guest advanced from the username prompt to the password prompt because charly typed at
it. That is the capability that did not exist.

**One observation worth recording, because it looked like a bug and was not.** An earlier
attempt in the same session typed 14 s after `vm start` and the characters never appeared,
while both commands still exited 0. The screenshot taken at that moment shows why:

```
Booting `Arch Linux'
Loading Linux linux ...
Loading initial ramdisk ...
[    0.087963] virt/tdx: TDX not supported by the host platform
```

The guest was still in early boot; the keys reached the emulated keyboard and **nothing was
reading them**. That is correct behaviour — `sendkey` delivers keystrokes, it does not
synchronise with the guest — and it is the reason `screenshot` comes first in the verb list.
The final run above polls with `screenshot` until the prompt is on screen rather than
sleeping a guessed interval.

### Negative controls — each guarantee removed, each test then fails

**NC1 — drop the Rock Ridge name preference** (report the ISO9660 name instead):
```
--- FAIL: TestSeedVolumeFiles_ReadsTheAuthoredNames
    answers volume does not list "authorized_keys" by its authored name;
    got [AUTHORIZ USER_CON.JSO USER_CRE.JSO USER_EMA.TXT USER_ENC.TXT USER_FUL.TXT]
```
The control that matters most: `seed cat user_configuration.json` becomes unanswerable, and
two long names can truncate to the *same* 8.3 name and silently collide.

**NC2 — silently skip a character that cannot be typed:**
```
--- FAIL: TestTextToGuestKeys_UntypeableCharacterIsAnError
    "echo héllo":  a character that cannot be typed must be an error, never a silent drop
    "echo \x01":   a character that cannot be typed must be an error, never a silent drop
    "grep — dash": a character that cannot be typed must be an error, never a silent drop
```
A dropped character runs a **different command** on the guest than the operator asked for,
and nothing on either side shows it happened — the worst outcome for a verb whose only job is
to tell you the truth about a guest.

**NC3 — pad a truncated capture instead of failing:**
```
--- FAIL: TestPpmFileToPNG_TruncatedCaptureIsAnError
    a truncated capture must be an error, not a partially black screenshot
```
A padded capture is a plausible-looking screenshot with a black band, and an operator reads
console text off it.

**NC4 — discard the monitor's reply text** (the QMP status is zero either way):
```
--- FAIL: TestQMP_SendkeyReportsAnUnknownKey
    an unknown key must be an error: qemu signals it in the reply text, not the status
```

### Test inventory (17 new tests)

The seed tests are driven through **charly's own writer** (`vmshared.WriteLabeledISO`), not a
hand-built fixture — so a divergence between what charly writes and what the verb reads
cannot pass. That divergence is exactly what sent this investigation to `isoinfo`.

Seed: `…_ReadsTheAuthoredNames`, `…_IsByteExact`, `…_MissingFileNamesWhatIsThere`,
`…_RejectsANonISO`.
Keys: `TestTextToGuestKeys_RealCommandLine`, `…_ShiftedAndUpper`,
`…_UntypeableCharacterIsAnError`, `TestGuestKeyToVirsh`, `…_UnknownKeyIsAnError`,
`TestEveryTypeableKeyTranslatesToVirsh`.
Screen: `TestPpmFileToPNG_RoundTrip`, `…_CommentsInHeader`, `…_TruncatedCaptureIsAnError`,
`…_RejectsAnotherFormat`.
QMP: `TestQMP_HandshakeAndHumanMonitor`, `…_ScreendumpConvertsToPNG`,
`…_SendkeyReportsAnUnknownKey`.

Two of these are **parity guards**, not case lists: `TestEveryTypeableKeyTranslatesToVirsh`
and the qemu half of `TestQMP_SendkeyReportsAnUnknownKey` each walk the whole printable ASCII
range through `TextToGuestKeys` and require every key it produces to be accepted by that
backend. Without them the vocabulary drifts from one backend and `vm type` fails mid-line,
leaving a half-typed command at a root prompt.

## Design notes a reviewer should check

- **No new runtime dependency — two removed.** The PPM→PNG conversion is written out rather
  than shelling to ImageMagick, and the ISO9660 reader rather than to `isoinfo`. A diagnostic
  that needs a second tool is a diagnostic people skip, which is how this gap persisted.
  `virsh` was already required by `vm console`.
- **The QMP client exists because govmm's cannot do this.** `vm_qemu.go` already uses govmm's
  QMP for `system_powerdown`, but it exposes a fixed catalogue of typed commands and **no**
  generic execute, so neither `screendump` nor `sendkey` is reachable through it. The new
  client is ~110 lines and skips async `event` frames — reading one as a reply is the classic
  bug in a hand-rolled QMP client, handled once rather than at each call site.
- **The key vocabulary is qemu-monitor-named; `guestKeyToVirsh` is the single translation
  point.** The two vocabularies disagree on exactly the keys a rescue session needs (`ret`,
  `spc`, the punctuation), so it lives in one place rather than being re-derived per call
  site (R3).
- **One monitor connection per burst.** Per-key connections are what make hand-driven `socat`
  typing unusable: the reconnect between keystrokes is slower than the guest's key repeat and
  reorders characters.
- **`seedPathFor` distinguishes the per-domain seed from the entity build seed** — they differ
  by the ssh public key, which is the whole reason `vm create` re-packs it. Reading the wrong
  one is exactly the class of mistake these verbs exist to prevent, so it is a flag, not a
  guess.
- **The ISO9660 reader is deliberately tiny** — one flat root directory of small files, which
  is exactly and only what an answers volume is. It prefers the Rock Ridge name and errors
  when it cannot read an image, rather than being a general ISO9660 implementation nobody
  asked for.
- **`vmBackendFor` degrades to libvirt when entity resolution fails.** These verbs are used
  when things are already broken; refusing to look at a guest because its entity no longer
  resolves is the least useful possible moment to be strict.

## What this does NOT cover, stated plainly

Disk inspection — `qemu-img convert` + `losetup` + `mount` — was also used by hand in the same
investigation, and it is where I made an actual wrong call: mounting `subvol=@` and nearly
concluding the SSH keys were missing, when `/home` is a separate `@home` subvolume. It is
**not** in this PR because it needs root and therefore a different mechanism (charly's
existing privileged-container path), not because it is unimportant. It is the next change,
not a deferred caveat on this one: nothing here is weaker for its absence, and no claim above
depends on it.

## Rulebook compliance

- **R1 — RCA every anomaly.** Four anomalies surfaced and all four were root-caused before any
  code moved: the PNG-vs-PPM format (traced to the device's framebuffer stream), the pixel
  shift (traced to `ppmToken` consuming its own terminator), qemu's zero-status key refusal
  (measured from qemu), and the keystrokes that "did not land" (traced by screenshot to a
  guest still in early boot — correct behaviour, recorded rather than smoothed over). None was
  classified "pre-existing" or "cosmetic".
- **R2 — Finish the whole cutover.** Both backends ship together. A libvirt-only version was
  the tempting scope and would have left every qemu-backend guest as undiagnosable as before.
- **R3 — No duplication.** One key vocabulary, one translation point, one ISO reader, one
  screen-format normalizer. The seed tests drive charly's own writer rather than a second copy
  of the format.
- **R4 — No workarounds.** No sleeps and no retries in the product. The QMP dial is bounded
  (15 s) because a hung monitor is itself a finding and a verb that blocks forever hides it;
  the test waits for qemu's socket with a bounded poll rather than a fixed sleep.
- **R4a — Fix the product first.** The documented-caveat version ("run `virsh screenshot` and
  convert it yourself") is what already existed informally, and it is why the gap lasted.
- **R5 — Delete legacy completely.** N/A — additive; no path replaced.
- **R6 — Git safety.** `git status` inspected before each commit; branched from a fresh
  `origin/main` rather than stacking on the open #12; no force-push, no hook bypass, no direct
  push to `main`.
- **R7 — Prove behavior, not compilation.** Four negative controls, each shown failing, plus
  the full live sequence with the guest's own screen contents quoted.
- **R8 — Preserve emitted artifacts.** The emitted artifacts are the PNG and the seed bytes;
  both are asserted — the PNG by pixel value, the seed bytes by sha256 against `isoinfo`.
- **R9 — Binary equals source.** N/A for this repo — plugin-vm is a candy, not a binary. It
  adds no new runtime OS dependency and removes the ImageMagick and `isoinfo` dependencies the
  manual workflow had.
- **R10 — Fresh disposable proof.** Not applicable in the bed sense: these are host-side
  operator verbs with no guest-side install step, so there is no disposable bed that could
  exercise them. What IS claimed, and what R10 is really asking for, is that the proof came
  from the **final committed tree** rather than an edited one: the live sequence above was
  re-run after `git commit`, against a domain started and stopped through charly's own verbs,
  and the working tree was clean (`git status --porcelain` empty) throughout.
