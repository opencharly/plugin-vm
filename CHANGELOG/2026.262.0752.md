# 2026.262.0752 — feat(vm): per-deploy VM-shape override (cpu/ram) over a from: template

## Summary of changes

A `from:` VM deploy may now state its own `cpu`/`ram`, inherited along the `from:` chain, over the `kind:vm` template it derives from — so MANY deploys can share ONE template at different sizes instead of each consumer duplicating the whole template (R3).

The motivating duplication is live: `omarchy-vm` exists twice — `distro-omarchy` (8G/4cpu, the keeper) and `eval-omarchy` (4G/2cpu, a lean 16-lane eval golden) — diverged in ISO pin, installer answer, AND size. Neither could derive from the other because a `from:` VM deploy silently ignored its own shape fields.

Concrete edits:

- `candy/plugin-vm/vm_shape_override.go` (new) — `vmShapeOverride(uf, entity, identity)` walks the created deploy's `from:` chain (nearest non-empty wins, per-field) and `applyVmShapeOverride` folds the result onto the template-resolved VM spec. Only cpu/ram: a template's `disk_size` builds the shared base disk ONCE, so a per-deploy disk_size cannot resize an already-built disk (and the spec leg removed the dead field).
- `candy/plugin-vm/vm_host_seams.go` — `hostConfigResolve` (the ONE resolve seam every `charly vm` command uses) applies the chain override after `ApplyCueDefaults`. A no-op when nothing in the chain declares a shape.
- `candy/plugin-vm/vm.go` — wires `VmCreateCmd`'s `--ram`/`--cpus`, which were **declared but never read**. Precedence: flags > deploy-from > template.
- `candy/plugin-vm/vm_shape_override_test.go` (new) — 4 tests: chain inheritance (two hops), nearest-wins, per-field partial shape, identity-scoping.

Consumes `#Deploy.cpu` from the sibling `spec` PR. The generated Go field name is unchanged (`Cpus`), so this compiles against the current pin and the runtime effect appears once a consumer pins both the new spec AND this plugin.
