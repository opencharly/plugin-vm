# 2026.270.0402 — fix(vm)!: key the per-host VM state by its deploy identity (sdk#301 consumer leg)

## Summary

The **plugin-vm consumer leg of sdk#301** (`v0.2026270.3`). sdk#301 retired the `vm:`-prefixed per-host overlay key: the per-host deploy state is now keyed by the deploy **IDENTITY** (the same string the tree/config/CLI use), with the VM **ENTITY** carried in the entry's `vm:` cross-ref. plugin-vm was still computing the retired `vm:<domainID>` key itself, so its writes no longer matched the identity-keyed readers — the failure my C6 bed surfaced.

- **`charly vm create`'s port_auto persist** now passes the IDENTITY (`domainID`) to `deploykit.SaveVmDeployState`, not `"vm:"+domainID`. Load-bearing: the compiled-in readers (`plugin-check`'s `FindVmDeployNode`/`ResolveVmSshPort` and `plugin-deploy-vm`'s `resolvePriorVmState`) all look up the identity key.
- **`charly vm destroy`** removes the IDENTITY-keyed entry when `--domain` names it; a direct `charly vm destroy <entity>` (no `--domain`) uses the `vm:<entity>` **addressing** form, whose From-scan resolves the deploy-keyed entry via its `vm:` cross-ref.
- **`charly vm build`** resolves its persisted `ExistingState` by the exact IDENTITY key (the retired `vm:<identity>` key's identity part) — not a scan by the `vm:` entity cross-ref, which is ambiguous when sibling beds share one entity.

**Dependency pins.** `candy/plugin-vm/go.mod` moves `github.com/opencharly/sdk v0.2026269.1204 → v0.2026270.152` **and** `github.com/opencharly/spec v0.2026269.1205 → v0.2026269.2150`. The spec move is **required by the sdk pin**: `sdk@v0.2026270.152`'s own `go.mod` requires `spec v0.2026269.2150`, so MVS resolves spec to 2150 (matching `go.sum`'s two new hashes).

Companion: **plugin-deploy-vm** (its `OpPostTeardown` `RemoveEntries` key), which the bed resolves at runtime.
