# 2026.253.0830 — fix(vm): a snapshot-anchored keeper restarts — chmod the active disk writable before qemu opens it, back to 0444 after

## Summary

The keeper-restart regression, fixed at the root: a snapshot-anchored keeper (e.g. check-omarchy-eval-base-inst) could not restart after a stop — qemu failed with "Could not open .../snapshots/golden/disk.qcow2: Permission denied".

Root cause: the shared-clone default chmods a captured golden snapshot 0444 (so parallel clones open it read-only with shared locks), but a snapshot-anchored keeper runs ON its golden as the ACTIVE disk — qemu opens the active disk read-write, so a 0444 active disk fails to start with EACCES.

The fix: the start/create paths chmod the active disk writable (0644) BEFORE qemu opens it, then back to 0444 AFTER the domain starts — the open fd is unaffected by the chmod, so the keeper keeps its writable fd while clones still get shared locks. The dance is the testable withSnapshotWritable helper; isSnapshotDisk detects the snapshot-anchored case; firstDiskSourceFile reads the active disk path from the domain XML.

## How tested (pasted)

**The live keeper-restart proof (a fresh charly rebuild with this plugin-vm, the golden at 0444):**

```
$ chmod 444 .../snapshots/golden/disk.qcow2 && stat -c "golden=%a" ...
golden=444
$ charly vm stop check-omarchy-eval-base-inst
Stopped VM charly-check-omarchy-eval-base-inst
$ charly vm start check-omarchy-eval-base-inst
Started VM charly-check-omarchy-eval-base-inst
$ virsh list --all | grep eval-base
 944   charly-check-omarchy-eval-base-inst   running
$ stat -c "%a" .../snapshots/golden/disk.qcow2
444
```

The golden at 0444 restarts (the pre-fix code fails with the exact EACCES above), and the golden is restored to 0444 after the start — the shared-clone benefit preserved.

**The unit lock (fails without the fix):**

```
$ go test -count=1 -run TestWithSnapshotWritable -v .
--- PASS: TestWithSnapshotWritable (0.00s)

$ go test -count=1 ./...
ok  	github.com/opencharly/plugin-vm/candy/plugin-vm	0.004s
```

TestWithSnapshotWritable asserts the snapshot is 0644 DURING the start fn and restored to 0444 AFTER (even when the fn fails) — it fails on the pre-fix code, which never chmodded the active disk.
