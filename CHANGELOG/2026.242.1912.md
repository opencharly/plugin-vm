# 2026.242.1912 — feat(vm): record the serial console, and read it with `vm console --dump`

## Summary

A headless guest was undiagnosable. Both existing verbs refuse — correctly — and between them
the guest is opaque:

```
$ charly vm screenshot <headless-vm>
VM … was defined with NO video device; add a libvirt.devices.video block to its kind:vm entity

$ charly vm console <headless-vm>
error: Cannot run interactive console without a controlling TTY
```

Hit live while diagnosing `omarchy-pacstrap-vm`. It is the worst class to be blind on: **every
bootstrap VM is headless by design** (`console=ttyS0,115200`, no graphics), so the guests whose
boot most needs reading were exactly the ones with no way to read it. A pty also keeps no
history, so a guest that already failed has nothing left to show — which is when a console
matters most.

## The change

The auto-synthesized serial device now carries a per-domain `<log>` file, and
`charly vm console --dump [-n N]` reads it.

```xml
<log file='…/charly-check-arch-vm/serial.log'/>
```

libvirt writes it as the guest emits, so the history survives the guest dying. It lives in the
per-domain state dir `vm create` already creates (`id_ed25519`, nvram, the per-domain seed), so
nothing new is provisioned and `vm destroy` removes it with the domain.

`-n` exists because a boot log is long and the interesting part is the end — reading the whole
thing into a caller's context is the failure the flag avoids.

**The path is derived inside this repo, not plumbed through `VmRuntimeParams`.** That struct
lives in the sdk, and a field there would have made this a cross-repo repin chain for one
string.

### Negative controls

**NC1 — revert to a serial with no log** (the state before this change):

```
--- FAIL: TestRenderDomainXML_SynthesizedSerialCarriesALog
    the synthesized serial carries no per-domain <log> element, so a headless guest's
    console is unreadable — `vm console` needs a TTY and a pty keeps no history.
```

**NC2 — make the log path domain-independent:**

```
--- FAIL: TestSerialLogPathFor_IsPerDomain
    two domains share one serial log ("…/serial.log") — their consoles would interleave
```

NC2 is the one that matters: two beds sharing a `kind:vm` entity get distinct domains, and a
shared log would interleave two guests' consoles into one file — a bug that would look like
corrupted output rather than a wrong path.

`TestDumpVmSerialLog_TailsWithLines` pins that `-n 2` prints the LAST two lines and `-n 0`
prints everything verbatim.

### Live

**The absent-log path, on a real pre-change domain** (created before this existed, so libvirt
will never write a log for it):

```
$ virsh dumpxml charly-check-omarchy-pacstrap-vm | grep -c "<log file"
0

$ charly vm console omarchy-pacstrap-vm --domain check-omarchy-pacstrap-vm --dump
charly: error: no serial log for charly-check-omarchy-pacstrap-vm at …/serial.log.
  A domain defined before serial logging carries no <log> element and libvirt will never
  write one for it. Recreate the domain (`charly vm create`) and the log appears from its
  next boot.
```

A bare "no such file" would have sent the reader hunting a missing directory. The fix is a
recreate, so the error says that.

**The positive path, on a domain created with this build:**


## Rulebook compliance

- **R1 — RCA every anomaly.** The gap was traced from a live failure (`Cannot run interactive
  console without a controlling TTY` on a VM that also had no video) to its cause: the
  synthesized serial had no `<log>`, and a pty has no history.
- **R2 — Finish the whole cutover.** The recording and the reader ship together. Either alone
  is useless.
- **R3 — No duplication.** `--dump` extends the verb that already owns the serial console
  rather than adding a second one; `--domain` resolution is the existing shared path.
- **R4 — No workarounds.** The rejected alternative was reading the pty directly, which steals
  bytes from anyone attached and still has no history.
- **R4a — Fix the product first.** The documented-caveat version ("attach a video device to
  your bootstrap VM") would add a GPU to every headless guest to work around a missing log.
- **R5 — Delete legacy completely.** N/A — additive; existing domains are unaffected and the
  verb tells them why.
- **R6 — Git safety.** `git status` inspected before the commit; the local `go.mod`/`go.sum`
  replaces used for the dev build were NOT staged; branched from a fresh `origin/main`; no
  force-push, no direct push to `main`.
- **R7 — Prove behavior, not compilation.** Two negative controls shown failing, plus both
  live paths — the absent-log error on a real pre-change domain, and a real boot log read back.
- **R8 — Preserve emitted artifacts.** The emitted artifact IS the log; it is asserted in the
  rendered XML and read back from a running guest.
- **R9 — Binary equals source.** The live run used a `task build:binary` stamped charly built
  from this branch.
- **R10 — Fresh disposable proof.** Not applicable in the bed sense — this is a host-side
  operator capability with no guest-side install step. The proof is the domain recreated from
  the final committed tree and its console read back, quoted above.
