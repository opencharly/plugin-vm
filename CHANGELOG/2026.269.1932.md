# 2026.269.1932 — feat(vm): emit the KubeVirt containerDisk disk layout + a --push delivery path

feat(vm): emit the KubeVirt containerDisk disk layout + a `--push` delivery path

## Summary

The charly VM box (`charly vm build`'s box-emission step) was emitted only with the
disk at **`/disk.qcow2`** — neither the KubeVirt containerDisk contract (KubeVirt
scans the **`/disk`** directory and boots the single file it finds there) nor the
in-image path `plugin-vm`'s OWN `container_disk` source reads back
(`/disk/disk.img`, `defaultContainerDiskPath`). So a charly-built VM box could not
be booted as a KubeVirt containerDisk — the gap plan WS-6.3 closes (the
charly-box → containerDisk payload path).

The sdk already ships the capability this needs (`deploykit.EmitVmBoxAt` +
`deploykit.ContainerDiskPath` / `VmBoxDiskPath`); the gap was purely in `plugin-vm`,
which always called the default path. This change wires the choice and adds the
delivery half:

- **`charly vm build --container-disk`** — emits the box with the disk at
  `/disk/disk.img` (`deploykit.ContainerDiskPath`) via `deploykit.EmitVmBoxAt`.
  Unset keeps the existing default (`/disk.qcow2`).
- **`charly vm build --push <ref>`** — after emitting, retags the local box to
  `<ref>` and pushes it with the engine so a target cluster can pull it. An explicit
  `--push` makes **both** the emit and the push load-bearing (a failure is returned);
  the default emit stays best-effort (a failed emit never fails the disk build).
- `boxInImagePath(bool) string` is the pure flag → path mapping;
  `pushVmBox(engine, src, dst)` is the delivery.

Files: `vm_box_emit.go` (emitter + push + mapping), `vm_build.go` (flags + the
`vmBuildDrive` seam + the drive's emit/push step), `vm_bake.go` (the extra emit arg),
`vm_box_emit_test.go` (tests below).

No spec/sdk pin is bumped: the pinned `sdk v0.2026269.1204` already carries
`EmitVmBoxAt`/`ContainerDiskPath`/`VmBoxDiskPath`.
