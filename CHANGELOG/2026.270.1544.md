# 2026.270.1544 — feat(vm): add 'vm import-container-disk' — pull a containerDisk into the shared VM-image cache

## Summary

Add **`charly vm import-container-disk <ref>`** — the standalone import primitive that `charly vm build`'s `container_disk` source (spec#171) is built on.

A containerDisk is an OCI artifact carrying a bootable guest disk (the KubeVirt containerDisk contract: the disk lives in a layer, by default at `/disk/disk.img`). The `container_disk` VM source pulls such an artifact **while building a `kind: vm` entity**. This command exposes that pull directly, so an operator can:

- **pre-warm** the shared, content-addressed VM-image cache (a large Fleet image pulled once, in CI or before a bed run) — a later `charly vm build` of a `container_disk` entity is then a cache **hit**;
- **inspect/verify** a published containerDisk (it prints the cache disk path + size + the manifest identity) without authoring a VM entity first.

It reuses the **ONE** pull engine (`pullContainerDisk`) — no second fetch path, no duplicated index→manifest resolution (R3). The source is synthesized with `containerDiskImportSource` into the same `#VmSource` shape a `container_disk` entity carries, so the cache key (`containerDiskCacheDir`) is shared with the build path **by construction**.

**Cache keying (the exact rule).** `containerDiskCacheDir` keys the shared cache by the **digest when the ref is digest-pinned** (`reg/x@sha256:…` → dir `sha256-<hex>`), and by the **sha256 of the ref string** for a tag ref (`reg/x:1` → dir `<hex>`). A digest-pinned ref therefore shares one cache entry across every consumer; a tag ref keys by the ref it was given, so the same artifact named by tag and by digest gets two entries — the intended behaviour of the shared engine, now pinned by `TestContainerDiskCacheDir_TagVsDigest`, which asserts the EXACT tag dir (`hex(sha256("reg/x:1"))`), the digest dir (`sha256-deadbeef`) and the digest's stability.

No `charly.yml` change: the grammar is prescanned from the Go command struct (the plugin-vm#50 precedent).

Files:

- `candy/plugin-vm/vm_import_container_disk.go` — the command + the pure `containerDiskImportSource` synthesis.
- `candy/plugin-vm/vm_import_container_disk_test.go` — the unit gates + the live-or-skip import.
- `candy/plugin-vm/vm.go` — Kong registration (`import-container-disk`; the diff is mostly `gofmt`'s struct-tag realignment from the new, longer field name).

## How tested

**The command ran LIVE through the real `charly` binary** (Kong registration + every flag executed), against ONE real `registry:2` on `localhost:5098` (`CONTAINERS_REGISTRIES_CONF` marking it insecure — no global config touched). A containerDisk fixture (a `FROM scratch` image with `/disk/disk.img` + `/disk/other.img`, one layer) was built + pushed, then imported by the CLI three ways:

```
$ charly vm import-container-disk --help
Usage: vm import-container-disk <image> [flags]
…
      --disk-path-in-image=STRING   Disk path INSIDE the image (default /disk/disk.img…)
      --cache=STRING                Override the container-disk cache root…
      --force                       Re-pull even when the cache already holds the artifact

# A. base import (--cache)
$ charly vm import-container-disk localhost:5098/cd-fixture:1 --cache /tmp/opencode/cd-cache
imported containerDisk localhost:5098/cd-fixture:1
  disk:     /tmp/opencode/cd-cache/f46d9a32…/disk.qcow2 (12 bytes)
  identity: sha256:81e5779e…
  cache:    /tmp/opencode/cd-cache/f46d9a32…
$ cat /tmp/opencode/cd-cache/*/disk.qcow2
DEFAULT-DISK

# B. --force (re-pull rather than the cache hit)
$ charly vm import-container-disk localhost:5098/cd-fixture:1 --cache /tmp/opencode/cd-cache --force
  disk:     /tmp/opencode/cd-cache/f46d9a32…/disk.qcow2 (12 bytes)
  identity: sha256:81e5779e…

# C. --disk-path-in-image override (extract a non-default path)
$ charly vm import-container-disk localhost:5098/cd-fixture:1 --cache /tmp/opencode/cd-cache2 --disk-path-in-image /disk/other.img
  disk:     /tmp/opencode/cd-cache2/f46d9a32…/disk.qcow2 (10 bytes)
$ cat /tmp/opencode/cd-cache2/*/disk.qcow2
OTHER-DISK
```

(The tag ref keys the cache by the sha256 of the ref string — `f46d9a32…` — matching the keying rule above.)
