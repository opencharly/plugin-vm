# 2026.249.0320 — fix(vm): stale-snapshot guard in BuildClone (R1, the grub-rescue regression)

## Summary

Three fixes in the clone/snapshot path (all surfaced by the nested-capture wave's instrument beds):

**1. Stale-snapshot guard (R1, the grub-rescue regression).** A snapshot whose backing chain was rebuilt AFTER the snapshot was captured is stale: the guest filesystem (e.g. btrfs) inside the snapshot references inodes in the OLD base data, so a clone boots into grub rescue ("inode not found") instead of the guest. The check-instrument-cachyos-vm bed hit exactly this: the golden snapshot (Sep 3) backed onto a cachyos-vm base disk rebuilt today, and the clone VM stalled at grub rescue for ~1h before the bed-runner timed out. `snapshotBackingStale` walks the snapshot's FULL qcow2 backing chain (`qemu-img info --backing-chain -U`) and reports the first backing file whose mtime is newer than the snapshot's capture time. `BuildClone` fails loudly with an actionable message naming the stale backing file + the refresh path (re-run the base bed that captured the snapshot). The check is transitive (the direct backing may be untouched while ITS backing was rebuilt) and read-only (`-U`) so a snapshot in use by a running clone is still inspectable.

**2. Shared-snapshot default (parallel clones).** External snapshot disks are now created read-only (0444) so multiple clone VMs can share the same golden snapshot disk in parallel (the nested-capture plan's parallel-testing requirement). `makeSnapshotWritable`/`makeSnapshotReadOnly` toggle the mode around the capture; the read-only default is what lets N clone beds clone from one golden concurrently.

**3. Stale-guard precision (R1, the false-STALE regression).** The registry stores `Created` at RFC3339 SECOND precision, but the guard compared the disk's `ModTime()` at nanosecond precision — a capture-finalization write landing sub-second after the truncated timestamp (e.g. base mtime 03:17:07.364Z vs Created 03:17:07Z) tripped a FALSE STALE on a valid snapshot. The guard now truncates the backing mtime to seconds before comparing, so only a genuinely later rebuild (a later second) is stale. This is the exact false-STALE the check-instrument-omarchy-vm bed hit after a fresh golden re-capture.
