# 2026.242.1648 — refactor(vm): drop rootLA, an identity wrapper that wrapped nothing

## Summary

`func rootLA(lba uint32) uint32 { return lba }` returns its argument unchanged. It survived
from a draft of the ISO9660 answers-volume reader where the root directory extent needed an
adjustment; it does not.

Caught by the `pr-validator` on #13 under B18 — *"`rootLA` is a trivial identity wrapper
(minor smell, not a blocker)"*. It landed because it was not a blocker; it is fixed now
rather than left, because the one call site it wraps is the root directory extent, and a
named wrapper there reads as if a conversion is happening. That is worse than no wrapper: it
invites the next reader to look for a rule that does not exist.

```diff
-	if _, err := f.ReadAt(dir, int64(rootLA(rootLBA))*isoSectorSize); err != nil {
+	if _, err := f.ReadAt(dir, int64(rootLBA)*isoSectorSize); err != nil {
-
-func rootLA(lba uint32) uint32 { return lba }
```

The seed tests are the ones that matter here and they are **unchanged**:

```

```

`TestSeedVolumeFiles_ReadsTheAuthoredNames`, `TestSeedVolumeFile_IsByteExact`,
`TestSeedVolumeFile_MissingFileNamesWhatIsThere` and `TestSeedVolumeFiles_RejectsANonISO`
all drive `readSeedRoot` through the root-directory extent this line computes, against an ISO
written by charly's own `vmshared.WriteLabeledISO`. They pass before and after.

**No negative control is offered, deliberately, and this is the honest reason:** a function
whose body is `return lba` cannot change behaviour when removed, so there is no guarantee to
break and no control that could distinguish the two versions. Manufacturing one would be
theatre. The existing byte-exactness tests are what prove the extent is still read from the
right offset — if the removal were wrong, `TestSeedVolumeFile_IsByteExact` fails, because a
misread root directory yields wrong extents for every file on the volume.
