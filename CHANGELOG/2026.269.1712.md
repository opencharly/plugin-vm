# 2026.269.1712 — feat(vm): the container_disk source arm's build engine (pull a Cua Fleet image)

## Summary

Implements the **`container_disk` source arm's build engine** in `plugin-vm`: charly can now
pull a bootable guest disk out of an **OCI artifact** and hand it to the UNCHANGED
cloud-init/SSH boot path. This is the consumer half of the Cua Fleet integration — spec#171
added the `#VmSource` arm, sdk#299 added the emitter; this drives the pull.

The motivating corpus is a **KubeVirt containerDisk** (a Cua Fleet image): an OCI image whose
layer holds the disk, by default at `/disk/disk.img` (the directory KubeVirt scans). No
KubeVirt is required — the disk is extracted locally and booted through the existing libvirt
path.

The engine:
- resolves an index → the amd64/linux platform manifest (`skopeo inspect --raw`);
- reads the layer digest + media type, locates the layer blob in skopeo's `dir:` layout;
- fetches the layer and streams the disk out of the tar (gzip-aware);
- asserts the extracted disk is qcow2 or raw (`qemu-img`);
- caches it **content-addressed** by the artifact identity (flock + atomic rename), so a
  re-pull of a pinned artifact is a cache hit and two beds never race;
- copies the cached base to the per-VM working disk and writes the SAME seed ISO the
  cloud_image arm does. The deploy path DOES change (review-round item 0): the per-domain
  cloud-init seed resolution and `needsPerDomainSeed` must cover `container_disk` exactly as
  they cover `cloud_image`, or the guest never receives charly's key — the defect the bed
  caught. Everything else in create/ssh/snapshot/clone is unchanged.

Wiring: `knownVmSourceKinds` gains `container_disk`; `resolveVmBuild` validates
`source.image` (cloud_image-like — nothing host-only to resolve); `runVmBuildDrive` gains its
`case`. The arm is **cloud_image-like** (a prebuilt disk seeded through cloud-init), so the
vm kind's `OpValidate` requires `distro:` exactly as for cloud_image (the sibling
plugin-substrate PR enforces that).

### A real defect the LIVE gate caught

The committed live pull test found a genuine bug: skopeo's `dir:` transport names blobs by
the **bare hex** digest (`sha256:07b912…` → `./07b912…`), while the engine built the path as
`sha256-<hex>`, so every pull failed at the layer read **after** a full registry round-trip.
`resolveLayoutBlob` now tries each known layout and falls back to a suffix scan.

### Review-round fixes (this head)

0. **The bed caught a real DEPLOY bug: the per-domain cloud-init seed was never attached.**
   `vm_create_orchestrate.go` resolved the per-domain seed for `cloud_image`/`clone`/`iso`
   but NOT `container_disk`, so a container_disk deploy's domain got no seed CD-ROM — charly's
   SSH key never reached the guest and the deploy never reached sshd (the bed hung on its SSH
   wait). The arm is cloud_image-like (a prebuilt disk seeded through cloud-init;
   `BuildContainerDisk` renders the seed), so it needs the same seed. Fixed in the per-domain
   seed resolution AND `needsPerDomainSeed`, gated on `CloudInit != nil || SSH != nil` — the
   same gate `RegenerateSeedISO` uses (an ssh-only VM still needs the seed carrying its key,
   which is this bed's shape). **This is the defect the R10 bed exists to catch: the WIRING,
   not the engine.**
1. **B12/R10 (real bug) — the cache identity was inconsistent.** The marker recorded the
   **layer** digest for a plain (non-index) manifest while the hit test compared the **ref**
   against it, so a plain-manifest re-pull never hit — contradicting the body's cache claim.
   Extracted `containerDiskCacheIdentity(platformDigest, raw)`: a resolved platform digest IS
   the identity; a plain manifest hashes its raw bytes. The hit test and the marker write now
   compute the SAME value, and `TestContainerDiskCacheIdentity_StableAndDistinct` asserts it is
   stable across a re-pull and distinct when the artifact changes.
2. **B14(a)/B18** — removed the no-op `dst` dance in the `buildLayer` test helper.
3. **B5/R1** — fixed two doc comments naming non-existent symbols
   (`ContainerDiskManifest` → `resolveContainerDiskManifest`; `skopeoCopyLayer` →
   `skopeoCopyToDir`) and the false "Exported for the unit gate" claim.
4. **staticcheck QF1011** — `extractDiskFromLayerTar` used `var src io.Reader = r`; now infers.
5. **B5/R1 — `containerDiskLayerDigest` enforced its documented contract.** The comment said a
   multi-layer manifest "is not a containerDisk", but the code returned `layers[0]` for any
   count ≥ 1. Now `len(m.Layers) != 1` is rejected, and
   `TestContainerDiskLayerDigest_RejectsNonSingleLayer` covers zero- and multi-layer payloads.
6. **B18 — the `hex` local in `resolveLayoutBlob` shadowed the `encoding/hex` package**; renamed
   to `hexDigest`.

## Rulebook compliance

- **R1** — every review finding dispositioned; the cache-identity bug was root-caused (write
  and read computed different values) and fixed with a single pure identity function, then
  covered by a test.
- **R3** — reuses the existing cloud-image boot path (cloud-init + seed ISO) and the
  `kit.FetchQcow2` cache discipline; no parallel mechanism.
- **R4** — the pull is owned by the plugin; the blob-layout question is resolved by PROBING the
  real layout (multi-candidate + suffix scan) rather than pinning a skopeo version's guess.
- **R5** — additive: a new `case` + a new `knownVmSourceKinds` member; no legacy arm removed.
- **Live or skip** — both live tests run against the REAL service or SKIP visibly.
- **R10** — the changed path executed through the dedicated disposable bed
  (`check-cua-container-disk-vm`), which drives the WIRING (the two new `case` arms), not just
  the engine function.
- Coverage: the unit gate is the pure-logic contract; the live gates + the bed are the
  integration contract.
