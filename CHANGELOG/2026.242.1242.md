# 2026.242.1242 — feat(vm): source.kind: iso — install a distro from its own installer, unattended

## Summary

Implements **`source.kind: iso`** — building a VM by running a distro's own official
installer. `BuildIsoVM` is the fourth build engine beside `BuildCloudImage` /
`BuildBootcVM` / `BuildBootstrapVM`, plus the resolve arm, the dispatch arm, and the
libvirt attachment.

Schema from spec#71; renderer from sdk#193; fetcher from sdk#194; runtime attachment from
sdk#195. This is the consumer that makes them a working feature.

### It is the simplest of the four engines, and that is the finding

Both earlier design passes assumed the installer had to be **ejected or detached** when it
finished, and specified machinery to detect that moment. None of it is needed:

1. Boot order is **disk first**. An empty disk is not bootable, so firmware falls through to
   the installer.
2. The installer writes the disk and powers off.
3. Every boot after, the disk boots. The ISO is never reached again.

Both cdroms stay attached forever and the reinstall-forever failure mode is **unreachable
rather than defended against**. This is upstream Omarchy's own documented recipe
(`--boot order='scsi0;ide2'` — the empty disk first, deliberately).

### The split: distro owns the FORMAT, vm entity owns the DATA

`installerSeedContext` is the data half and **knows nothing about archinstall**. A renderer
that guessed the format from the distro name is the failure `validateSourceDistro`'s own
comment records as having burned this codebase.

### Guards, not conveniences

**The plaintext password is `crypt()`ed before it can reach the context**, which is all
`RenderInstallerSeed` ever sees. `openssl passwd -6` deliberately: Go's stdlib has no
`crypt(3)`, `x/crypto` has no SHA-crypt, and charly carrying its own password-hashing
primitive would be worse than a host-tool dependency. Passed on **stdin**, never argv, so
it is not visible in `ps`.

**`encrypt: true` with only a `password_hash` is rejected** — LUKS takes the passphrase, not
a hash, so that configuration cannot work.

**No credential at all is rejected** — an account with no password is either unreachable or
wide open depending on the distro. `defer_provisioning` is the third, explicit option.

**`kernel_args` is rejected, not ignored** — see below.

**The changed code paths were executed LIVE**, against a real 5.8 GiB Omarchy ISO and a real
libvirt domain. A previous revision of this body claimed `fully tested and validated` on
`go test` alone and was correctly BLOCKed for it; this run is the answer to that.

The binary was built from this branch plus the unmerged **charly#485** (the omarchy
`installer:` block, without which no seed renders at all). Those `replace` directives are

### 4 — THE INSTALL COMPLETED

An earlier revision of this body reported the guest booting the medium but the installer
never starting, and claimed only `analysed on a live system` for it. That has since been
root-caused and fixed, and the install now runs to completion.

The stall was **not** in this engine. It was three defects in the *answers* this engine
renders — charly's `installer:` templates omitting keys archinstall indexes with no default
(`sector_size`, `mount_options`) and a `#` comment inside a YAML block scalar landing in the
JSON. All three surfaced only on the guest's tty1, behind the ISO's `quiet splash` cmdline,
and all three are fixed in charly#485.

With those fixed, from a seed this engine built:

```
disk before the install: 197248 bytes
disk after:              6135939072 bytes
```

The guest **rebooted from disk into its own greeter** — a graphical password prompt, where
the live ISO instead autologins to a root shell — and `user` / `user`, the credentials this
engine hashed to `$6$`, logged in to a working Omarchy desktop: Hyprland with the Quickshell
bar, workspaces, clock, tray, wallpaper and the first-run cards.

**Both cdroms stayed attached the whole time and nothing ejected anything.** That is the
disk-first boot order doing exactly what it was designed to do, observed rather than argued:
blank disk falls through to the installer, installed disk boots, ISO never reached again.

Omarchy's own `omarchy-cidata-load` accepted this engine's volume without modification:

```
$ ls /dev/disk/by-label/
OMARCHY_202608  cidata
$ omarchy-cidata-load; echo LOADRC=$?
LOADRC=0
```

One thing this run did surface that is **not** fixed and is filed rather than papered over:
at BOOT the ISO's `.automated_script.sh` does not find the cidata drive (its `udevadm
settle` does not cover the enumeration of a SATA cdrom that has not been queued yet), falls
back to the interactive wizard, and exits. Running the same entry point a minute later
succeeds — which is how the install above was driven. That is an Omarchy ISO race, not this
engine, and it is opencharly/distro-omarchy#4 with the full evidence.

### 4 — a defect in this PR's own code, found by that attempt

`#VmSource`'s iso arm **declares `kernel_args`** and `BuildIsoVM` did not implement it. I set
`console=ttyS0,115200` to get serial diagnostics on the stalled install and the serial line
stayed silent — because the field reached nothing.

Implementing it means rewriting the boot config inside a multi-GiB ISO. Nothing shipping
needs that. But **accepting the field and doing nothing is not an option**: the operator
reaching for `kernel_args` is by construction already debugging, and gets exactly the
silence they were trying to fix.

That failure shape cost this cutover real time **twice today** (spec#79 and plugin-distro#6,
both silent field drops). So it now **errors**, as a precondition before the fetch — a test
asserts that ordering, so nobody waits on a 5.8 GiB download to learn their field is
unsupported.

### R9 — the openssl dependency

`hashPasswordSHA512` shells out to `openssl passwd -6`, which is a new runtime OS
dependency of the charly binary. It is declared in **opencharly/charly#488**, which adds
`openssl` to all four real `depends` lists (archlinux, rpm, deb, apk) — it cannot be
declared from this repo, since `packaging:` lives on charly's own candy.

`depends`, not `optdepends`: an operator authoring `installer.password` without openssl gets
a hard failure with no hash, and meets it only after a multi-GiB ISO download.

**Seven negative controls, each confirmed to fail the intended test:**

| Control | Result |
|---|---|
| don't hash the plaintext | `the PLAINTEXT password reached the seed context — it would land on the answers volume verbatim` |
| drop the no-credential guard | `an installer with no password, password_hash or defer_provisioning must be an error` |
| drop the LUKS guard | `encrypt: true with only a password_hash must be an error — LUKS needs the passphrase, not a hash` |
| ignore `kernel_args` instead | `source.kernel_args must be rejected for iso VMs while it is unimplemented` |
| cdrom boot device first | `boot order is cdrom-first — the guest would reinstall over itself on every boot` |
| both cdroms on one target | `the two cdroms must have distinct targets (sda, sdb)` |
| emit the cdrom boot device unconditionally | `a VM with no installer must not gain a cdrom boot device` |

The last is the important one: a boot-order change leaking into every existing
`cloud_image` / `bootc` / `bootstrap` VM would be a serious regression hiding inside a
feature addition.

## Two defects in OTHER repos that this work uncovered

Both were found by running `charly vm build`, and both are silent drops of the same class:

- **opencharly/plugin-distro#6** — `resolveDistro`'s hand-written field copy dropped
  `disk_layout` and `installer`.
- **opencharly/spec#79** — `ResolveInherits` dropped `DiskLayout`, `Installer`,
  `InheritPackages` and `Raw` on every distro with a parent.

Together they meant **the btrfs subvolume feature has been inert since it merged** (spec#72,
plugin-vm#6, plugin-vm#7, charly#476 — all green, all doing nothing). Both fixes ship with
field-walking parity guards.

**This PR depends on both.** Until they merge, `charly vm build` on an iso source reports
`distro "omarchy" declares no installer` against a distro that plainly declares one.

## Rulebook compliance

- **R1 — RCA every anomaly.** The `vm build` failure was chased through two repos
  (plugin-distro#6, spec#79) rather than worked around at the first layer that would have
  hidden it. The install stall was root-caused to three defects in the *answers*, not in
  this engine, and each is named with the exact error the installer printed.
- **R2 — Finish the whole cutover.** All four legs of the source kind ship together: the
  build engine, the resolve arm, the dispatch arm and the libvirt attachment. The
  `knownVmSourceKinds` list and the `default:` error message were both updated so no path
  still claims three kinds. `kernel_args` is the one declared field this engine does not
  implement, and it is rejected rather than deferred silently.
- **R3 — No duplication.** `FetchArtifact` rather than a second downloader,
  `RenderInstallerSeed` rather than an omarchy-specific renderer, `parseDiskSizeBytes`
  rather than a second size parser, the existing cdrom attachment path rather than a
  parallel one. `qemuImgCreateBlank` is genuinely new: no existing helper creates a disk
  with no backing file.
- **R4 — No workarounds.** No sleeps, no polling for the install to finish, no marker
  files. The disk-first boot order makes the terminating condition structural.
- **R4a — Fix the product first.** `kernel_args` is the test of this rule: rather than
  document it as a limitation, it now errors with the reason, so nobody authors a field
  that does nothing. Implementing it means repacking a multi-GiB ISO and is filed as such.
- **R5 — Delete legacy completely.** A speculative `installerSeedDigest` helper was written
  and then **deleted** rather than shipped unused.
- **R6 — Git safety.** `git status` inspected before each commit; the dev `replace` on sdk
  was dropped and replaced with a published pin before committing (`grep -c '^replace'` = 0
  in the committed `go.mod`). No force-push, no direct push to `main`.
- **R7 — Prove behavior, not compilation.** Seven negative controls, each shown to fail the
  intended test — including one where the test PASSED with the behaviour deleted and had to
  be rewritten. Plus a live build, a live create, the real domain XML, and a completed
  install.
- **R8 — Preserve emitted artifacts.** The emitted artifacts are the answers volume and the
  domain XML, and both are validated at their real boundary: `isoinfo`/`blkid` on the
  written ISO, `virsh dumpxml` on the defined domain, and Omarchy's own
  `omarchy-cidata-load` accepting the volume (`LOADRC=0`).
- **R9 — Binary equals source.** The proof binary was built with `task build:binary`'s own
  steps from this branch, and `openssl` — the one new runtime OS dependency, from
  `hashPasswordSHA512` — is declared in opencharly/charly#488, since `packaging:` lives on
  charly's candy and cannot be edited from here. The binary additionally carried unmerged
  charly#485, without which the seed cannot render; see the tier note.
- **R10 — Fresh disposable proof.** The live run used a freshly built binary against a
  freshly created domain and a fresh 40 GiB qcow2, destroyed and undefined afterwards. All
  seven negative controls ran against deliberately broken trees restored from backups. It
  is NOT yet a `disposable: true` bed — `check-omarchy-iso-vm` is blocked on
  distro-omarchy#4, the ISO's boot-time cidata race.
