# 2026.242.1725 — fix(vm): an iso guest's ssh alias records no host key

## Summary

An installer-driven guest changes its SSH host identity **exactly once**, and pinning across
that change makes it permanently unreachable.

1. The live installer environment brings up its own sshd with freshly generated host keys —
   Omarchy's ISO has cloud-init do this, visible on its console.
2. The first thing to connect pins that key under `accept-new`.
3. The installer finishes and the guest reboots into the **installed** system, whose host
   keys are entirely different.
4. Every connection after that fails:

```
Offending ED25519 key in .../known_hosts:1
Host key for [127.0.0.1]:40563 has changed and you have requested strict checking.
Host key verification failed.
```

Polling cannot recover from that, so the readiness gate burns its whole cap and the deploy
never starts.

**Measured on a real guest:** with the stale line present the managed alias returns *"Host
key verification failed"*; with the one line removed the **same** alias connects immediately
and reports `hostname=omarchy`, `root=btrfs`, `sshd=enabled`.

## The fix belongs on the alias — two earlier attempts proved it

This took two wrong placements to see, and both are worth recording:

| Attempt | Why it failed |
|---|---|
| clear `known_hosts` at `charly vm create` | runs **before** the install — it cleared a file that did not exist yet, and the bad pin was written afterwards |
| relax the ssh args inside plugin-deploy-vm's `prepare-venue` | fixed only **that** consumer; the bed runner's own readiness gate runs first, over the same alias, and pinned the installer's key before prepare-venue was ever reached |

The alias is what **every** consumer uses — the bed runner's readiness gate,
plugin-deploy-vm's `prepare-venue`, and `charly vm ssh` alike. One place, every consumer,
one mechanism (R3). The second attempt is reverted on its own branch rather than left
alongside this.

`/dev/null` rather than a relaxed policy: `accept-new` still applies, so the first connection
is accepted exactly as before, and nothing is ever **recorded** to conflict with. What is
given up is host-key continuity for a per-domain loopback guest whose login key charly
generated itself — weighed against a guest that is otherwise unusable.

### The "initramfs hang" — RCA complete, and it was not a hang

An earlier revision of this body reported that the guest "hung in its initramfs" after
installing, and called it "new and undiagnosed". The reviewer was right to block on that.
It has now been root-caused, and the answer is that **there was no hang**.

**The two messages are both non-fatal, and say so:**

```
ERROR: Failed to open encryption mapping: The device PARTUUID=b226eaec-… is not a LUKS
       volume and the crypto= parameter was not specified.
Unable to resume from device '/dev/vda2' (254:2) offset 1639945, continuing boot process.
```

The first comes from mkinitcpio's `encrypt` hook, which Omarchy ships in its initramfs
unconditionally; with `encrypt: false` there is no LUKS volume for it to open, so it reports
and moves on. The UKI's own command line confirms there is nothing to decrypt — it carries
`root=PARTUUID=… rootflags=subvol=@ rw rootfstype=btrfs` and **no `cryptdevice=`**. The
second is the `resume` hook finding no swap signature. Both end the boot sequence normally.

**What was actually wrong was the host-key pin this PR removes.** With the fix in place the
same bed, on the same seed, now installs unattended and is reachable:

```
$ charly check live check-omarchy-iso-vm
VM: charly-check-omarchy-iso-vm (ssh user@127.0.0.1:36041)
  PASS  check the guest is the INSTALLED system, not the live ISO
  PASS  check root is a btrfs @ subvolume, not the live ISO's overlay
  PASS  check all four subvolumes are mounted where the answers placed them
  PASS  check the ESP is vfat at /boot, not /boot/efi
  PASS  check limine is on the ESP, registered, and is what the machine booted
  PASS  check limine's config carries the answers' ESP path and root device
  PASS  check snapper is configured for root and limine-snapper-sync is enabled
  PASS  check the account from user_credentials.json exists and is in wheel
  PASS  check the hostname from user_configuration.json was applied
  PASS  check the timezone from user_configuration.json was applied
  PASS  check the git identity from the seed's two .txt files was applied
  PASS  check the omarchy runtime and the desktop stack the ISO ships are installed
  PASS  check sshd is enabled AND running — which only authorized_keys turns on

13 steps: 13 passed, 0 failed, 0 skipped
```

From inside that guest:

```
$ charly vm ssh check-omarchy-iso-vm -- 'head -3 /etc/os-release; findmnt -no SOURCE,FSTYPE,OPTIONS /'
NAME="Omarchy"
PRETTY_NAME="Omarchy"
ID=omarchy
/dev/vda2[/@] btrfs rw,relatime,compress=zstd:3,discard=async,space_cache=v2,subvolid=256,subvol=/@
```

`ID=omarchy` is only true of an installed guest — `omarchy-settings` replaces
`/etc/os-release`, and archiso's live environment reports `ID=arch`. The full upstream stack
is present at the versions the ISO ships: `limine 12.6.0-1`, `limine-mkinitcpio-hook
1.37.1-1`, `limine-snapper-sync 1.31.0-1`, `snapper 0.13.1-3`, `sddm 0.21.0-7`, `uwsm
0.26.7-1`, `hyprland 0.56.2-1`, `quickshell 0.3.1-1`, `omarchy 4.0.1-1`, `omarchy-settings
4.0.1-1`.

So the paragraph this replaces was wrong in its conclusion, and the block that called it out
was correct. There is no undiagnosed failure attached to this PR, and nothing is parked.

### The bed now PASSES — this fix plus its counterpart

This fix was necessary but not sufficient on its own: the stanza has a SECOND writer,
`plugin-deploy-vm`'s `prepare-venue`, which overwrote what `vm create` publishes here. That is
fixed in `opencharly/plugin-deploy-vm#7`, and with the pair in place the disposable bed goes
green end to end:

```
[vm-build]           PASS after 1.476s
[vm-create]          PASS after 2.456s
[deploy-add]         PASS after 10.732s
[bring-up-members]   PASS after 0s
[check-live]         PASS after 5.566s
[update]             PASS after 4m53.443s     ← FAILED at 13m11s and 13m10s without the pair
[check-live-rebuild] PASS after 4.839s        ← 13 steps: 13 passed, 0 failed, 0 skipped
[cleanup]            PASS after 3m1.393s
[cleanup-members]    PASS after 0s
PASS (steps=9)
```

The stanza was watched at every phase rather than inferred from the verdict. With the pair,
`UserKnownHostsFile /dev/null` survives `vm create`, `deploy-add`, and the rebuild's own
`vm create` (visible as the port rolling 46179 → 36005), and the per-domain `known_hosts` is
**never created at any point**. Without them a key was pinned 8 seconds after the stanza flipped.

**What this PR contributes to that result:** the `/dev/null` policy itself. Remove this change
and `vm create` publishes a real `known_hosts` path, which is what the counterpart PR is then
careful to preserve — so the pair is what closes the bed, and this half is the half that
decides the policy. The two are independent commits in independent repos and neither is
deferred: both are open, both are proved by the same run.

**A second, unrelated condition, named rather than parked:** `sudo -n` in that guest fails with
`sudo: a password is required`, because a stock Omarchy install grants password-required sudo.
That is `opencharly/plugin-deploy-vm#6`, measured there, and it only bites a deploy that
installs packages — this bed installs none, which is why it passes 13/13 with that condition
present.

## Rulebook compliance

- **R1 — RCA every anomaly.** Two anomalies, both root-caused, neither parked. (a) The
  unreachable guest: traced to the one-time SSH host-identity change, after two placements
  that treated symptoms. (b) The "initramfs hang" an earlier revision of this body reported
  as undiagnosed: traced to mkinitcpio's unconditional `encrypt` and `resume` hooks finding
  nothing to act on — both messages are non-fatal, the UKI cmdline carries no `cryptdevice=`,
  and the guest reaches a full multi-user system. That paragraph was wrong and is replaced
  above with the measurement that settles it.
- **R2 — Finish the whole cutover.** One mechanism at the shared point; the superseded
  prepare-venue attempt is reverted in the same push rather than left as a second path.
- **R3 — No duplication.** That revert is this rule: one problem, one fix, at the place every
  consumer shares.
- **R4 — No workarounds.** Not a retry, not a sleep, not a bed weakened to pass. The
  condition that could never become true is removed.
- **R4a — Fix the product first.** The documented-caveat version ("clear known_hosts by hand
  after an iso install") would have made the defect permanent.
- **R5 — Delete legacy completely.** The per-domain `known_hosts` is not written-then-ignored
  for iso guests; it is not written.
- **R6 — Git safety.** `git status` inspected before the commit; no force-push, no direct
  push to `main`. The superseded branch was deleted, not force-overwritten.
- **R7 — Prove behavior, not compilation.** Two negative controls covering both directions,
  plus the live stanza and the absent `known_hosts`.
- **R8 — Preserve emitted artifacts.** The emitted artifact is the ssh_config stanza; it is
  read back and asserted, from the real writer.
- **R9 — Binary equals source.** N/A — plugin-vm is a candy, and this adds no runtime OS
  dependency.
- **R10 — Fresh disposable proof.** Met, jointly. The `disposable: true` `check-omarchy-iso-vm`
  bed reaches `PASS (steps=9)` with this change and its counterpart
  (`opencharly/plugin-deploy-vm#7`) in place, including `[check-live-rebuild] 13/13` against the
  guest the disposable rebuild installed from a blank disk. Stated precisely: the bed needs BOTH
  — this PR decides the policy, the counterpart stops it being overwritten — and neither is
  deferred; both are open and both are proved by the same run, quoted above.
