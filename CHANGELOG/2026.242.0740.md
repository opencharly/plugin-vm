# 2026.242.0740 — feat(disk): btrfs subvolumes and a per-distro ESP mount point

## Summary

`EmitDiskBuildScript` could only produce a **bare** root filesystem with the ESP hardcoded
at `/boot/efi`. Two distro layouts cannot be expressed that way, and Omarchy needs both:

- **Subvolumes.** An ISO-installed Omarchy guest has `@`, `@home`, `@log` and `@pkg`, and
  its `fstab` and limine cmdline reference `subvol=@`. A bootstrap VM built on a bare btrfs
  filesystem can never be snapshotted, and does not match what the distro ships.
- **The ESP mount point.** Omarchy mounts its ESP at **`/boot`**, not `/boot/efi`. That is
  what `limine-entry-tool` and `ESP_PATH` assume, and a loader written to the wrong place
  leaves an unbootable disk **with no build-time error at all**.

### Every file in the diff

| File | What changed |
|---|---|
| `candy/plugin-vm/vm_disk_layout.go` | `DiskLayout` gains `Subvolumes []Subvolume` and `EspMountPoint string`; the btrfs arm, the exit trap and the finalize tail render them; validation added |
| `candy/plugin-vm/vm_disk_subvolume_test.go` | **new** — the byte-parity gate, the ext4 no-op gate, the Omarchy layout, and five teeth cases |

### The ordering is the correctness

A btrfs subvolume **cannot** be created through a mount that is already pinned to a
different subvolume, and mounting the root subvolume first leaves nowhere to create its
siblings. So the sequence has to be: mkfs → mount the top level → create every subvolume →
**unmount** → mount the `/` subvolume at `Mnt` → mount the rest beneath it. The exit trap
and the finalize tail unmount **deepest-first**, or the root subvolume is busy when
`qemu-img` converts.

### Nothing else changes — and that is tested, not asserted

`Subvolumes` nil reproduces the previous script **byte for byte**, and `EspMountPoint`
defaults to `/boot/efi`. So arch, cachyos, debian, ubuntu and fedora build exactly the disk
they built yesterday. `TestEmitDiskBuildScript_NilSubvolumesIsByteIdentical` compares
against a **verbatim capture of the old output** held in the test file — a behavioural diff
there is a regression in someone else's distro, not a feature, and the test says so.

## How tested

### 1. The generated script, rendered

```
set -euo pipefail
mkdir -p /out
RAW=/out/disk.raw
truncate -s 40G "$RAW"
LOOP=$(losetup --find --show --partscan "$RAW")
trap '
  umount /mnt/boot 2>/dev/null || true
  umount /mnt/home 2>/dev/null || true
  umount /mnt/var/log 2>/dev/null || true
  umount /mnt/var/cache/pacman/pkg 2>/dev/null || true
  umount /mnt 2>/dev/null || true
  losetup -d "$LOOP" 2>/dev/null || true
' EXIT
parted -s "$LOOP" \
  mklabel gpt \
  mkpart ESP fat32 1MiB 512MiB \
  set 1 esp on \
  mkpart root btrfs 512MiB 100%
partprobe "$LOOP" || true
mkfs.fat -F32 "${LOOP}p1"
mkfs.btrfs -f "${LOOP}p2"
mkdir -p /mnt
# btrfs subvolume layout. The top level (subvolid=5) is mounted first ONLY to create the
# subvolumes, then unmounted -- a subvolume cannot be created through a mount that is
# already pinned to a different subvolume, and mounting the root subvolume directly would
# leave nowhere to create its siblings.
mount "${LOOP}p2" /mnt
btrfs subvolume create /mnt/@
btrfs subvolume create /mnt/@home
btrfs subvolume create /mnt/@log
btrfs subvolume create /mnt/@pkg
umount /mnt
mount -o subvol=@,compress=zstd,noatime "${LOOP}p2" /mnt
mkdir -p /mnt/home
mount -o subvol=@home,compress=zstd,noatime "${LOOP}p2" /mnt/home
mkdir -p /mnt/var/log
mount -o subvol=@log,compress=zstd,noatime "${LOOP}p2" /mnt/var/log
mkdir -p /mnt/var/cache/pacman/pkg
mount -o subvol=@pkg,compress=zstd,noatime "${LOOP}p2" /mnt/var/cache/pacman/pkg
mkdir -p /mnt/boot
mount "${LOOP}p1" /mnt/boot
# >>> install rootfs <<<
```

```
# <<< install rootfs >>>
sync
umount /mnt/boot
umount /mnt/home
umount /mnt/var/log
umount /mnt/var/cache/pacman/pkg
umount /mnt
losetup -d "$LOOP"
trap - EXIT
qemu-img convert -O qcow2 "$RAW" /out/disk.qcow2
rm -f "$RAW"
```

Every subvolume was created and mounted with the `subvol=` the script asked for
(`subvol=/@`, `/@home`, `/@log`, `/@pkg`); **the ESP mounted at `/mnt/boot` as vfat**, with
`/mnt/boot/efi` asserted absent and a loader file actually written to it; and the
deepest-first teardown left both loop devices clean.

**What this run does and does not cover, stated plainly.** Two loop devices stand in for
`${LOOP}p1` and `${LOOP}p2`. The *partitioning* is unchanged by this PR and cannot be
exercised in this container at all: partition nodes for a loop device need udev, which a
`--privileged` podman container does not have, so `mkfs.fat` fails on `/dev/loop0p1` no
matter what (`partprobe` and `partx -a` were both tried). Everything the PR **does**
change — the subvolume sequence, the ESP mount point, and the teardown order — is executed
above exactly as `EmitDiskBuildScript` emits it. charly's real `RunPrivileged` builder is
where the partition step already works today and is untouched here.

  landing; the VM disk path was read before it was edited.
- **R1 — RCA every anomaly.** Three surfaced, all root-caused rather than hidden.
  (a) Running the **whole** generated script in an ad-hoc container failed at
  `mkfs.fat: unable to open /dev/loop0p1`: partition nodes for a loop device need udev,
  which a podman container has none of. `partprobe` and `partx -a` were both tried and
  neither helps, so the live proof uses two loop devices instead — which exercises every
