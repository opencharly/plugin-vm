# 2026.251.1105 — fix(vm): idempotent from:-drive clone build (kills the overlapping-lane overlay write-lock race)

## Summary

Fixes the measured `from:`-drive overlay race at the root. Code-level RCA (traced): the drive path already resolves its backing to the **SNAPSHOT STORE disk** (`snapshots/<tag>/disk.qcow2`, opened read-only via `qemu-img create -F qcow2 -b` — empirically proven to succeed even while a lock is held on the backing), and the refcount model is already wired (bump on clone, decrement on teardown, delete refused while referenced, re-capture isolation). The single defect: `BuildClone` ran `qemuImgCreateOverlay` **unconditionally on every build**, re-creating the shared per-entity target overlay `output/qcow2/<entity>/disk.qcow2` while a sibling lane's domain holds it open read-write → `Failed to get "write" lock` on overlapping lanes (measured: 16/21 runs in the eval-omarchy 16-lane verification wave; reproduced 1:1 with qemu-img 11.1.1).

**Fix:** idempotent skip-or-create — the `cloneDiskFresh` probe skips overlay creation when the target already materializes the resolved snapshot; rebuild only when the snapshot was **re-captured after the overlay**. This makes the runtime match the documented contract (vm skill: "fresh per-VM qcow2 with the parent snapshot's external disk as backing chain"): existing clones keep the linked overlay while the golden changes freely — no side effects while the snapshot lives; new clones pick up the new snapshot; deletion remains refcount-guarded.
