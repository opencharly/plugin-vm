# 2026.240.2034 — feat(libvirt): render the full GPU surface, the gl rules and qemu:override

## Summary

The renderer leg of **B6 — the GPU configuration surface**, and the one that closes it.

`mapVideo` carried 5 of the ~15 attributes libvirtxml's `DomainVideoModel` / `DomainVideoAccel`
/ `DomainVideoDriver` expose; `mapGraphics` wired `<gl>` only as spice's `enable=` string; and
`<qemu:override>` had no expression at all — which is why Spike 3 had to hand-inject that XML.

Renders now: `device=`, `ram`/`vram64`/`vgamem`, `blob=`, `edid=`, `accel2d=`, the acceleration
`rendernode=`, `<resolution>`, `<driver>`, the device `<alias>`, egl-headless' and dbus' `<gl>`,
and `<qemu:override>` for the QEMU device properties libvirt models no element for —
`drm_native_context`, `hostmem`, `max_hostmem`, `venus`.

Also bumps libvirtxml **v1.12002.0 → v1.12005.0**, which is what makes `<model device='…'/>`
expressible. The diff between them is **12 added lines and zero removals** across all three
changed files (`domain.go`, `network.go`, `capabilities.go`) — `DomainVideoModel.Device` plus a
CPU `energytune` struct.

## Four defects found by validating against libvirt's own RNG

Not by reading the Go structs, which cannot show any of them. By rendering the domain and
handing it to `virt-xml-validate` against `/usr/share/libvirt/schemas/domain.rng` on this host
(libvirt **12.6.0**):

| defect | what I wrote | what libvirt's RNG says |
|---|---|---|
| `blob=`, `edid=` | `yes` | **`virOnOff`** — unlike `primary=`/`accel3d=` *in the same element*, which are `virYesNo` |
| `<qemu:property type=>` | `number` | vocabulary is **`string \| signed \| unsigned \| bool \| remove`** |
| dbus `address=` + `p2p=` | both accepted | modelled as a **`<choice>`** — mutually exclusive |
| `<gl>` on spice/dbus | `enable` optional | **required** (egl-headless has no `enable` at all) |

Each would have produced a domain libvirt refuses to define, with a Relax-NG error blaming
`<devices>` or `<frontend>` rather than the attribute.

A **fifth** was caught by the existing regression test rather than the RNG: the established
`boolPtrToYesNo` collapses `nil` into `"no"` (documented as matching the legacy renderer). Wiring
the new tri-state fields through it stamped `blob="no" edid="no" accel2d="no"` onto **every VM in
the corpus** — `TestRenderDomainXML_ArchCloudBase` broke on its exact-fragment match for
`<acceleration accel3d="no">` when `accel2d` appeared beside it. The new fields use a
nil-preserving helper; `primary=`/`accel3d=` keep the legacy spelling so existing XML is
byte-identical.

## Why three rules are render errors and not CUE cross-rules

The natural home for *"a `<gl>` block is meaningless on a vnc graphics device"* is a cross-rule
in `#LibvirtGraphics`. Written the obvious way, `if type == "vnc" { gl?: _|_ }`, it makes
`cue exp gengotypes` emit:

```go
type LibvirtGraphics any /* TODO: IncompleteKind: _|_ */
```

The generator evaluates the definition with `type` still abstract, so every branch stays
unresolved, the field kinds reduce to bottom, and it degrades the whole struct. **That compiles**
— every graphics block would silently decode into an untyped map. So the rules run here, at the
exact point where the field would otherwise be dropped, and where the message can say why.

An override whose alias no device declares is a hard error for the same reason: libvirt accepts
it and applies it to **nothing**, which is the single most likely authoring mistake and
completely silent. The message names the unmatched key *and* the aliases that do exist.

## R3: one predicate, not two

`ensureVirtiofsSharedMemory` becomes `ensureSharedMemoryBacking`. virtiofs and a blob virtio-gpu
need the same `memfd`/`shared` backing for the same reason — something maps guest RAM — so the
coupling is one predicate rather than two near-identical functions. Auto-pairing means an author
enabling `blob` never discovers the requirement from a failed VM start.

`blob-native-context` is Spike 3's working configuration expressed entirely in charly YAML, and
its override carries a bool, a string, a positive int and a **negative** int, so all three
property types are exercised.

`TestRenderDomainXML_UnsetTriStatesAreOmitted` is the bound on the whole change: a video device
declaring only what candies declare today must render exactly the attributes it rendered before,
and it asserts the *absence* of `blob=`, `edid=`, `accel2d=`, `rendernode=`, `<alias>` and
`qemu:override`.

`TestRenderDomainXML_OverrideWithMatchingAliasIsAccepted` exists so the rejection test cannot
pass by rejecting everything — the classic way a validation test goes vacuous.

## A note on the namespace spelling

Go's encoder emits `<override xmlns="http://libvirt.org/schemas/domain/qemu/1.0">` rather than
the `qemu:`-prefixed form libvirt's docs show. Both are the same namespace to a namespace-aware
parser, and the rendered domain **validates against libvirt's own RNG**, so the assertions target
the namespace URI and structure rather than a prefix the encoder does not control. I checked this
rather than assuming it — my first test asserted `<qemu:device …>` and was wrong.
